# Пул обработчиков на горутинах

Лабораторная работа по системному программированию. Модуль `lab/concurrency`, только стандартная библиотека Go 1.21+.

Восемь заданий с числами от 1 до 8. Каждое задание «ждёт внешний ресурс» 200 мс, затем считается квадрат числа. Итог: набор пар «исходное число, квадрат».

Реализовано три вещи: последовательная обработка, пул обработчиков с ограничением числа горутин, отмена работы через контекст с возвратом частичного результата.

## Запуск

```bash
go mod tidy
go run .
```

Без аргументов выполняется весь набор сценариев и замеры, около 15 секунд.

Отдельные сценарии:

```bash
go run . seq                 # последовательно, 8 заданий
go run . pool 4              # пул из 4 обработчиков
go run . pool 2 -w 8         # число обработчиков по умолчанию для pool
go run . timeout 300ms       # пул с бюджетом времени
go run . cancel              # контекст отменён до старта пула
go run . bench 3             # по 3 прогона на режим, медиана
go run . -delay 50ms seq     # ускорить имитацию ожидания
go run . help                # справка
```

Вывод одного сценария выглядит так:

## Как это устроено

`processTask` запускает `time.NewTimer` и ждёт в `select` одного из двух событий: сработал таймер или отменился контекст. Таймер освобождается через `defer` и вспомогательную функцию `stopTimer`, которая заодно вычитывает канал уже сработавшего таймера.

Пул оформлен структурой, а не набором отдельных функций:

```go
type pool struct {
	workers int
	jobs    chan int
	results chan Result
	wg      sync.WaitGroup
}
```

Методы: `start` запускает отправителя заданий, обработчиков и закрывающий надзиратель, `feed` раздаёт задания, `work` обрабатывает очередное задание, `finish` закрывает канал результатов после `wg.Wait()`, `drain` собирает результаты в вызывающей горутине. Внешняя функция `runPool` осталась тонкой обёрткой, поэтому интерфейс из задания сохранён.

Ошибки обёрнуты через `%w` и проверяются в тестах через `errors.Is`, поэтому исходная причина (`context.DeadlineExceeded`, `context.Canceled`, `ErrWorkers`) не теряется, а к ней добавляется контекст: на каком этапе остановились.

Сортировка сделана на `slices.SortFunc` с `cmp.Compare`, печать таблицы замеров на `text/tabwriter`, чтобы столбцы не разъезжались при разной длине чисел.

## Кто закрывает каналы

| Канал | Закрывает | Когда |
| --- | --- | --- |
| `jobs` | горутина `feed` через `defer close(p.jobs)` | после выдачи всех заданий или при отмене контекста |
| `results` | горутина `finish` после `p.wg.Wait()` | когда все обработчики вызвали `Done`, то есть отправителей больше нет |

`results` читает только `drain` в вызывающей горутине, поэтому закрытие не пересекается с записью. Отправка результата идёт через `select` с `ctx.Done()`, иначе при отмене обработчик мог бы навсегда зависнуть на небуферизованном канале.

## Замеры

Три прогона на каждый режим, в таблице медиана. Вывод `go run . bench 3`, Linux, 2 ядра, Go 1.27:

| Режим | Прогоны | Медиана | Ускорение |
| --- | --- | ---: | ---: |
| последовательно | 1.603s 1.604s 1.604s | 1.604s | 1.00x |
| пул, 1 обработчик | 1.603s 1.603s 1.603s | 1.603s | 1.00x |
| пул, 4 обработчика | 401ms 401ms 401ms | 401ms | 4.00x |

Пул из 4 обработчиков уложился в две волны по 200 мс вместо восьми. На одном ядре результат такой же: задания не считают, а ждут, поэтому спящая горутина ядро не занимает.

## Тесты

```bash
go test -timeout 15s ./...
go test -race -timeout 30s ./...
```

Результат прогона: `ok lab/concurrency 1.112s` и `ok lab/concurrency 2.165s`.

Что проверяется:

| Тест | Проверка |
| --- | --- |
| `TestSequentialReturnsAllPairs` | все восемь пар по эталону, сумма 204, время не меньше восьми заданий |
| `TestSequentialStopsWhenCanceled` | отменённый контекст даёт `context.Canceled` и пустой набор |
| `TestPoolWorkerCounts` | 1, 2, 4, 8, 16 обработчиков, корректные пары и порядок по возрастанию |
| `TestPoolSpeedupWithFourWorkers` | пул из 4 минимум вдвое быстрее последовательного прохода |
| `TestPoolRejectsBadWorkerCount` | 0 и отрицательные значения дают `ErrWorkers`, набор `nil` |
| `TestPoolHandlesEmptyInput` | пустой список не вешает пул |
| `TestPoolReturnsPartialOnTimeout` | таймаут 330 мс: часть набора, `context.DeadlineExceeded`, быстрый выход |
| `TestPoolCanceledBeforeStartReturnsFast` | отмена до старта: возврат за секунды, а не за 1,6 с |
| `TestPoolStopsAllWorkers` | после таймаута число горутин возвращается к исходному |
| `TestNewPoolValidatesWorkers` | конструктор пула и поле `workers` |
| `TestSortByInputKeepsOrder` | сортировка по исходному числу |

Тестам не нужно ждать по 200 мс на задание: вспомогательная `shortDelay` уменьшает задержку до 20 мс и возвращает прежнюю через `t.Cleanup`.
